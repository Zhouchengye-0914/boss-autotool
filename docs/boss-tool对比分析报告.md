# boss-tool 与 boss-job-assistant 对比分析报告

报告时间：2026-07-19  
分析对象：`D:\projects\boss-tool`、`D:\projects\boss-job-assistant`

## 1. 结论摘要

`boss-tool` 的优势是业务覆盖更广，已经包含职位搜索 API 监听、岗位筛选、详情补充、自动招呼、聊天轮询和简历发送，适合作为“功能原型与选择器素材库”。它当前不适合直接承担大批量无人值守执行：成功判定偏宽松、失败任务会从队列直接删除、每日额度不持久化、队列写入非原子、选择器和点击策略较激进，且缺少自动化测试。

`boss-job-assistant` 的优势是执行内核更稳健：配置化、任务模型明确、断点原子写入、三次重试、上海自然日额度、可注入节奏控制、唯一可见元素约束、结构化结果、环境冻结、dry-run 和单元测试均已实现，并已完成 5 条真实发送测试。其主要不足是业务入口较窄：尚未正式整合搜索扫描、岗位评分、聊天监控和主动发简历。

推荐路线不是二选一，而是以 `boss-job-assistant` 为主工程，把 `boss-tool` 中经过收紧和测试的“扫描、筛选、聊天监控、简历发送”能力作为输入适配器和可选执行模块迁入。不要反向把可靠调度逻辑塞回 `boss-tool` 的现有主循环。

## 2. 核心能力对比

| 维度 | boss-tool | boss-job-assistant | 判断 |
|---|---|---|---|
| 项目形态 | 根目录扁平模块，交互式单流程 | 包结构、YAML 配置、CLI 子命令 | 后者更适合维护和测试 |
| 浏览器 | DrissionPage，独立 profile；未固定 Chrome 路径和调试端口 | 固定 Chrome、专用 profile、固定端口、持久 UA、启动诊断 | 后者更可复现 |
| UA | 每次从池中随机；当前池仅 Chrome 124 | 首次随机后持久化；匹配 Chrome 150 | 后者更利于会话稳定 |
| 任务来源 | 监听 `joblist` API，自动扫描和筛选 | JSON 任务输入，已有 32 条候选和 5 条实测任务 | 前者覆盖更广，后者边界更清晰 |
| 队列 | pending/completed 两态 | success/failed/skipped、attempts、reason、时间 | 后者状态语义更完整 |
| 断点写入 | 直接覆盖 JSON | 临时文件 + `os.replace()` | 后者抗中断能力更强 |
| 损坏文件 | 捕获异常后使用空队列 | 保留损坏文件并停止 | 后者避免静默丢失历史 |
| 重试 | 配置存在，但主循环失败后直接删除 pending | 每任务最多 3 次，重启继续剩余次数 | 后者符合需求 |
| 每日额度 | 内存计数，重启清零 | 断点按 Asia/Shanghai 统计成功数 | 后者可靠 |
| 节奏 | 8–20 秒；每 10 次休息；8% 长停顿 | YAML 控制 3–15 秒；每 20 成功休息；10% 长停顿 | 两者都有，后者可测试、符合约定 |
| 鼠标点击 | 坐标移动后由调用方直接 click；异常静默降级 | 滚动、元素内部随机偏移、移动、短停顿、动作点击 | 后者实现更统一 |
| 元素消歧 | 找到第一个即使用，存在文本/坐标兜底 | 只接受唯一、可见、正尺寸元素 | 后者误点击风险较低 |
| 成功确认 | 输入回车即返回成功；即使 greeting 失败仍记录成功 | 点击发送后检查状态、消息或输入区变化；不确认则失败 | 后者明显更可靠 |
| 已沟通处理 | 直接返回 `already` 并计入 completed | 已修复：已建立会话不等于招呼语已发送 | 后者口径准确 |
| 简历 | 有发送按钮、序号选择、自动回复原型 | 当前只处理沟通过程中的指定简历弹窗 | 前者功能广，后者策略保守 |
| 聊天监控 | 已有轮询与自动发简历原型 | 尚未实现 | 前者领先，但需验证 |
| 异常截图 | Logger 有函数，但未形成统一“先截图再处理”链路 | 页面阶段化截图并写入结果 | 后者审计更完整 |
| 输出 | completed.csv、errors.csv，字段较少 | 每次尝试结果 CSV、最终错误 CSV、断点 JSON | 后者可追踪性更强 |
| CLI | `input()` 驱动，关闭浏览器退出 | validate/dry-run/browser-check/run/status/environment-check | 后者更适合自动调度 |
| 测试 | 未发现测试目录 | 14 项 unittest 全部通过 | 后者更可靠 |
| 环境控制 | 依赖 `jsonpath`，无冻结校验 | 仅使用既有依赖，完整 freeze 校验 | 后者符合环境硬约束 |

## 3. boss-tool 的主要优点

1. 搜索页 API 监听比纯 DOM 扫描更高效，可以得到职位 ID、薪资、地区、Boss 信息等结构化字段。
2. 业务链路较完整，从搜索、过滤到沟通，再到收到回复后发送简历，方向符合最终产品形态。
3. 已有薪资、标题关键词、公司黑名单和 Boss 活跃度等筛选入口，适合扩展到数据分析、管培生、数据运营和 AI 岗位策略。
4. 现有运行数据证明浏览器、部分搜索和部分沟通链路能够工作，不是纯空壳。

## 4. boss-tool 的关键风险

### 4.1 成功判定会产生假阳性

`greeter.py` 在 `_handle_greeting_popup()` 返回失败后仍继续执行，随后无条件调用 `record_send()`、写成功 CSV 并返回 `True`。输入框执行回车后也直接返回成功，没有核对消息气泡、成功提示或按钮状态。

`resume_sender.py` 同样存在“未出现弹窗可能已经一键发送”的推定成功。这类推定在真实网页中容易把草稿、弹窗打开、会话建立误记为发送成功。

### 4.2 completed 的统计口径不等于成功发送

主流程把 `result == "already"` 也调用 `mark_completed()`。当前数据中 `task_queue.json` 有 8 个 completed，而 `completed.csv` 只有 2 条成功记录，证明 completed 混合了多种语义，不能用来统计真实投递量。

### 4.3 重试配置没有真正接入主循环

虽然配置有 `MAX_RETRY_PER_TASK = 3`，但沟通失败后主循环直接 `remove_from_pending()`。任务既没有尝试次数，也没有最终跳过原因；重启后不会自动恢复该失败任务。

### 4.4 每日额度重启即失效

`RateController` 在初始化时把今日发送数设为 0，未从 CSV 或断点恢复。一天内重启程序会重新获得 300 次额度，存在突破预期上限的风险。

### 4.5 持久化不够安全

队列使用普通 `open(..., 'w')` 直接覆盖。写入中断可能损坏 JSON；读取损坏后又自动使用空队列，容易造成历史任务状态丢失。

### 4.6 元素操作偏激进

多个定位逻辑返回首个匹配元素，没有统一检查唯一性、显示状态和正尺寸。`_handle_boss_popup()` 最后会按页面坐标兜底点击，可能误触其他控件。现有错误 CSV 已出现两次“元素没有位置及大小”。

### 4.7 运行与环境可复现性不足

未固定 Chrome 可执行文件、调试端口和 UA 状态；UA 写成 Chrome 124，而实际浏览器是 Chrome 150。项目直接依赖 `jsonpath`，但没有依赖冻结或环境一致性命令。

## 5. boss-job-assistant 的主要优点

1. 成功、失败、最终跳过的状态分离，尝试次数和原因进入断点。
2. 成功断点先原子落盘，再追加 CSV，降低重复发送风险。
3. 每日额度只统计成功任务，并基于上海自然日从历史断点恢复。
4. 同一任务最多三次重试，失败不会在第一次就永久丢失。
5. 页面元素必须唯一、可见、有正尺寸；未知或无法消歧时不发送。
6. Chrome 路径、profile、调试端口、UA 和节奏都可配置，UA 会持久化。
7. dry-run 不启动浏览器、不睡眠、不写正式断点。
8. 环境冻结检查已在真实主机上下文通过，14 项单元测试全部通过。
9. 已完成 5 条真实沟通测试，并在实测中识别和修复了“继续沟通误判成功”和“草稿误判历史消息”。

## 6. boss-job-assistant 当前不足

1. 目前正式输入仍是 JSON 文件，缺少内建搜索扫描器。
2. 岗位筛选策略较弱，还没有把关键词、薪资、地区、Boss 活跃度形成配置化评分器。
3. 聊天监控与收到回复后发简历尚未正式实现。
4. 简历选择目前只覆盖沟通链路弹窗，没有完整的聊天页主动发送附件流程。
5. BOSS 前端选择器仍需要随着真实页面变化持续维护，尤其是 iframe/弹层与聊天消息气泡。
6. 当前结果 CSV 保留了开发测试期间的误判记录；这是有价值的审计历史，但正式运行前应启用独立生产日志文件或增加 correction 字段。

## 7. 推荐整合方案

### 第一优先级：保留可靠执行内核

继续以 `boss-job-assistant` 的配置、模型、调度器、断点、节奏、动作、输出和环境检查为主，不替换这些模块。

### 第二优先级：迁移职位扫描能力

把 `boss-tool/job_scanner.py` 改造成 `JobSource` 输入适配器：

- 用标准库遍历字典替代 `jsonpath`，避免新增依赖。
- API 监听失败时提供 DOM 扫描后备方案。
- 输出统一转换为 `JobTask` 或 `JobCandidate`。
- 保留原始职位字段，生成稳定任务 ID。
- 搜索和沟通分成两个 CLI 阶段，扫描不会自动触发发送。

### 第三优先级：建立岗位匹配评分

将岗位方向配置为数据分析、管培生、数据运营、AI 产品/运营，并综合标题关键词、描述技能、薪资、地点、学历经验、Boss 活跃度打分。低分任务进入候选 CSV，不直接沟通。

### 第四优先级：谨慎迁移聊天和简历模块

- 只处理明确的未读消息，不以 DOM 中任意红点判断。
- 指定简历必须按名称唯一匹配，不使用数组序号作为唯一依据。
- 发送后必须确认消息气泡或附件状态。
- 每个联系人维护独立幂等键，避免重复发送简历和自动回复。
- 遇到验证码、安全验证或未知弹窗时暂停，不坐标兜底点击。

### 第五优先级：正式运行前隔离测试数据

为开发、真实小批量、正式运行分别设置 progress 和 CSV 路径；历史测试日志保留只读，不与生产统计混用。

## 8. 最终判断

- 如果目标是“现在就稳定执行明确的职位任务”：选择 `boss-job-assistant`。
- 如果目标是“快速参考搜索和聊天功能怎么组织”：参考 `boss-tool`，但不要直接大批量运行。
- 如果目标是最终完整产品：以 `boss-job-assistant` 为底座，分阶段吸收 `boss-tool` 的扫描、筛选、聊天、简历能力，并为每项新增能力补充 dry-run、状态确认和单元测试。

建议下一步先迁移职位扫描与筛选，不先迁移自动发简历。扫描是只读能力，价值高、风险低，也能直接为数据分析、管培生、数据运营和 AI 方向持续生成任务候选。
